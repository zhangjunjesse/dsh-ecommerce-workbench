# Decision: 工作流引擎（注册表 + 调度 + 执行日志）

Status: current

## Problem

工作台里已经有若干「按一次按钮跑一次」的模块，但没有任何东西能**在没有人按按钮的时候做事**：用户希望有一处可以管理工作流——设成周期执行或手动触发，并查看每次执行的日志。

需求同时给了一个关键约束：**工作流的内容由代码写死**（后续逐个指定再开发），用户不创建工作流，只管理它。因此要交付的是一台**引擎**，而不是某个具体工作流。

## Decision

新增 `工作流` 模块，位于左侧导航主分组、**T恤二创 正下方**（它在自己干活，而不是像分割线下方的模块那样只是替别人存素材）。

**工作流是代码，不是数据。** `lib/workflows.js` 是唯一声明工作流的地方，每个定义形如 `{ id, name, description, run(ctx) }`。该模块的 `BUILT_IN_WORKFLOWS` **刻意留空**——交付的是基础设施，而不是一个假装在干活的占位工作流。加一个工作流是代码改动：写好定义、列进数组，它就以自己的设置与历史出现在界面上，客户端一行都不用改。注册时即校验定义，形状不对**在挂载时就抛**（当面、立刻、在刚写下它的人面前），而不是几小时后某个定时运行在暗处失败。

用户拥有的是**方法体之外的一切**：是否启用、周期、手动触发、运行历史。

**周期只有两种形状**：间隔（每 N 分钟，1…10080）或每天固定墙钟时间（HH:MM）。**cron 被明确否决**——它会引入解析器、时区模型和一整套夏令时语义，去回答一个目前没人问的问题。下次执行时间**每次从墙钟重算**，而不是在上一次时间上累加，所以长期运行的宿主不会漂移，每天固定时间在夏令时切换后仍落在它自己声称的那个钟点上。

**启用不会立刻触发**：打开开关或改周期时，下次执行时间重算为「从现在起一个间隔」。因此拨动开关不会造成意外运行，改动前遗留的旧时间戳也不会在调度器下一次看它时立刻触发。着急就用「立即运行」。

**错过的周期只跳过、绝不补跑**：调度器活在宿主进程里，DSH 不在运行时工作流不会执行（没有向操作系统注册任何东西）。停机期间到点的周期，在历史里**记一条**「已跳过」，然后周期继续往前走。补跑意味着 DSH 一启动就突发一串真实（且可能计费）的执行，与「每 30 分钟」被理解成的意思正好相反。宿主在运行中同样适用：忙过三个间隔也只跑一次，不是三次。

**同一工作流同时只跑一次**：上一次还没结束时到点的调度被跳过并计数，而不是排队——排队会让慢工作流堆出无界积压，而每一次排队都是一次真实执行。跳过的次数在该次运行结束时写进它的日志，所以这件事可见，却不会每个 tick 写一条历史记录。「停用」停的是**周期**，不禁止「立即运行」。

**每次尝试都留下记录**：触发方式（手动/周期）、状态（运行中/成功/失败/已跳过）、开始时间、耗时、工作流返回的一行摘要，以及它自己的日志行。历史表**不带**日志行（`GET /ecom/api/workflow/runs`），单次日志走 `GET /ecom/api/workflow/run?id=…`，这样渲染一张表不会把整个日志档案搬一遍。日志在运行期间留在内存、**结束时只写一次**——每行一次写意味着一个话多的工作流会把 `state.json` 重写几千遍。全部有上限：每工作流保留最近 **50** 次（`ECOM_WORKFLOW_RUN_KEEP`）、总数 **500** 次（`ECOM_WORKFLOW_RUN_TOTAL`）、单次 **500** 行（`ECOM_WORKFLOW_LOG_LINES`）、单行截断 2000 字符。

**工作流无法绕过全局并发出图闸**：交给它的 `provider` 是包装过的——每个方法都去申请共享的 `withGeneration` 槽位，所以「没有不受管的路径」是**结构上成立**的，而不是靠约定。`withGeneration` 本身**刻意不暴露**给工作流：把它套在外面（外层一个槽位，内层再调被包装的 provider）会让两个并发工作流各持一个槽位、又各等第二个，在并发上限为 2 时**死锁**。

**刻意不做**：不提供「停止运行中工作流」按钮——已经在飞行中的 provider 调用无法真正中断，一个按了没用的按钮比没有按钮更糟。宿主退出时正在跑的那次，在下一次挂载时被收尾为「失败（宿主在这次运行期间退出）」，而不是永远挂在历史里假装还在运行。

持久化上，`state.json` 只存**配置**（`workflows: [{id, enabled, schedule, nextRunAt, lastRunAt, lastStatus}]`），运行历史与日志另存 `workflow-runs.json`：`/ecom/api/state` 是被轮询的、且客户端直接渲染它返回的记录，把几百条运行日志塞进去会让每次轮询都拖着整个历史。配置与历史各有一条写队列，互不阻塞。

回归过程中顺带修掉两个真实竞态（详见 README「Why the store now writes atomically」）：`writeFile` 先截断再写导致并发读可能读到半个 JSON（现改为临时文件 + rename 原子替换，两份文档都改）；以及生成任务在 `await store.update` **之前**就把 `job.status` 置为 `done`，使轮询者在看到「已完成」的瞬间去读 `/ecom/api/state` 可能拿不到那一行（现改为先落盘、再发布 done）。

## Alternatives considered

- **用户自定义工作流（在界面上编排）**：需要一套编排 DSL、参数模型、校验与权限，而且一旦工作流逻辑确定下来，这些几乎都要返工。用户已明确「工作流内容到时候我给，你开发」，故本期只做引擎。留的口子：`ctx` 已经是稳定的接口（`log` / `store` / 受管的 `provider` / `trigger` / `now`），后续真要参数化，加的是定义里的字段与界面，不是重写引擎。
- **cron 表达式**：最灵活，但要自带解析器、时区与夏令时处理，维护成本高，且当前没有需求。已否决，保留两种形状。
- **把调度器做成独立进程 / 系统计划任务**：DSH 不运行时也能跑。但那意味着工作流在无人使用 DSH 时消耗真实额度，且需要一套独立的部署与权限模型。已否决，改为**明确**进程内调度 + 界面与文档都写清「只在 DSH 运行期间生效」。
- **错过就补跑**：会让 DSH 启动瞬间突发执行（可能大量消耗额度）。已否决，改为记一条「已跳过」。
- **每次日志行都落盘**：崩溃时能留下部分日志，代价是每个话多的工作流把 `state.json` 重写几千遍。已否决；改为运行期间留内存、结束时写一次，代价（宿主中途死掉会丢掉该次的日志，但那次运行本身仍被记录并收尾）已写在代码注释里。
- **给工作流暴露 `withGeneration`**：看似更灵活，实则会因嵌套信号量而死锁（见上）。已否决，只给被包装的 `provider`。
- **「停止运行」按钮**：无法真正中断在飞的调用，等于假功能。已否决。

## Consequences

- 导航主分组变为 印花提取／印花二创／T恤二创／工作流；分割线下方不变。`viewNames` 与 `viewEls` 是按下标对齐的平行数组，因此新增了 `test/client-render.test.js` 的一条不变量用例，专门防止「导航与视图列表错位」（错位会让某个标签显示成另一个视图，且只在插入点之后悄悄发生）。
- 未注册任何工作流时，`工作流` 页显示**空态**并说明工作流由代码注册、以及注册后会得到什么。这是预期结果，不是坏页面；代价是这一版无法在真实浏览器里演示卡片、周期选择器与日志面板——因此补了 `test/client-render.test.js`，用最小 React 桩构建真实组件树来覆盖这些路径（空态、卡片、周期控件、四种运行状态、日志面板）。
- 引擎在测试中通过**注入式注册表**驱动（`createHandler(store, provider, { registry })`），所以不需要为了「能验证」而给用户塞一个占位工作流。
- 周期调度只在 `dsh web` 运行期间生效；DSH 关闭期间的周期记为「已跳过」，不补跑。
- 工作流可以读写 `store`、可以出图（经全局并发闸）。出图会消耗 ToAPIs 额度，因此「不补跑」这个决定同时是一条成本保护。
- `handler` 上挂出 `handler.workflows`（运行器）与 `handler.registry`，宿主用**同一个**运行器启动调度器——另建一个运行器会各自持有 in-flight 表，「同一工作流同时只跑一次」的保证就会在每个运行器内部各自成立而整体失效。

## Verification

- `node --check` 全部 7 个 lib 文件 → Passed。
- `node --test "test/*.test.js"` → **70/70 passed**（宿主 67 + 客户端 3）。工作流部分覆盖：定义校验、周期归一化与日期算术、配置（启用/设周期/重算/清空，以及「被拒绝的周期不改变任何东西」）、手动运行（日志/摘要/结束时已落盘）、失败、单飞（409 指向正在飞的那次）、调度（到点跑一次、未到点不跑、停用不跑）、错过周期（恰好一条「已跳过」、未执行、周期已推过该点）、重叠（跳过计数、无积压）、日志上限、历史保留、清空、崩溃恢复、provider 经共享闸而 `withGeneration` 不可达、配置与历史在重开 store 后仍在。
- 稳定性：宿主测试连跑 30 轮、两个文件连跑 8 轮，全绿；此前用于定位的两个偶发失败（生成任务 done 竞态、`/state` 跨源读写竞态）已修掉并有对应用例。
- 客户端渲染：`test/client-render.test.js` 用最小 React 桩真实构建组件树，断言空态文案、卡片名称/说明/启用态/运行中态、两种周期的中文摘要、日志行、运行摘要、「已跳过」及其原因，以及导航与视图列表对齐。
- 组合体检 `dsh --profile web --dump-config` → 包含 `ecommerce-workbench` 条目并解析到 `dsh-ecommerce-workbench-mock` 包（沿用 DECISION-0001 的方式）。
- 浏览器端到端：刷新 profile 拷贝并重启 `dsh web` 后，`工作流` 标签可打开并显示空态；注册第一个工作流后，卡片、周期设置、立即运行与日志面板在真实浏览器中可用。
