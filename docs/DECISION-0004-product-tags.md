# Decision: 成品库标签（款式级 + 批量 + 筛选）

Status: current

## Problem

成品库现在只能**看**：它把流水线跑出来的产物按「商品（参考图分组）→ 款式（合成图）→ 成片」摆成货架，能翻、能看详情、能删单张，但没有任何地方能表达**关于货的判断**。

而用户要做的判断恰恰全是关于货的：哪些要上架、上架到哪些平台、哪些暂时不做。这些判断今天只能记在工作台之外的脑子里或别的地方，而货架会持续变大（当前 689 个款式、2.4 GB 字节、每跑一组再加一两百件），「上次那批准备发 TikTok 的到底是哪几个颜色」很快就会变成一个回答不了的问题。

需要的是一种**灵活的、能自己定义、能批量施加、能用来筛选**的标记；同时这种标记必须活得过工作流的重跑，也必须经得起手改 `state.json`、恢复备份、删组删图这些既有操作。

## Decision

给成品库加**标签**：用户自己定义标签，打在货架卡片上，按标签筛选，并支持批量打。

**标签打在「款式」（货架卡片）上，键是 `groupKey|tshirtFile`。** 这是本次设计的根，其余都是它的推论。

- 卡片就是货架展示、单张删除、批量选中的**同一个单位**，键与客户端已经在算的 `card.key` 完全一致——宿主可以拿成片记录直接校验这个键真实存在（`workflow-outputs.json` 里存在同 `groupKey` + 同 `tshirtFile` 的一行），所以**标签不可能指向不存在的货**，不需要额外的存在性簿记。
- 备选是流水线自己的逻辑键 `colorwayKey = cw:<款式id>|<印花文件>`：它能活过「强制重跑」（重跑会生成新的合成图文件，文件名变了，按文件名的键就成了孤儿）。但它要经 `tshirtPhoto → 款式` 反查，而 117/307 条老记录根本没有那些字段，于是会多出「解析不出来」的第三种状态——**一个标签要么在要么不在，不该有第三态**。故否决逻辑键，改为：重跑这个代价由 v2 的「按逻辑键把旧卡片的标签继承给新卡片」补掉，而不是现在就引入三态。
- 普通重跑（续跑）复用已有产物、文件名不变，标签安全；只有**强制重跑**会另生成一套卡片，旧卡片与旧标签都还在（流水线本来就写明「新写行而不是覆盖已付费的行」）。

**标签是款式级的，但界面提供商品级的批量。** 一个商品（参考图分组）的 N 个款式各持自己的标签，弹框里给一个「应用到本商品全部款式」——一次点完，而不是让用户点 N 次，也不是让同一个判断在商品和款式两层各存一份、然后互相打架。这一下**只加不删**：它不会剥掉别的款式自己已有的标签，因为一个批量动作顺手删东西，是这类界面最不该有的意外。

**筛选是多选 AND，另有一个「未打标签」。** 选中的若干标签要求卡片**全部**持有（「待上架」+「TikTok」= 两个都有），这正是选品时真正要问的问题；`未打标签` 是另一个问题（还有什么没看过），它**替换**而不是叠加筛选——和任何条件求交永远为空。筛选条上每个标签后面的数字是**当前商品范围内的**款式数，所以胶囊和它下面的货架永远在说同一件事；它不是联查数（「再加上这个条件还剩多少」是另一个更贵的问题，而且答案会随着点击一直变）。

**标签用 id 标识，名字只是显示。** 改名不动任何一条赋值，这是「灵活管理」的前提；名字全局唯一（重名会让筛选条上出现两个读起来一样的胶囊，而它们其实不是一回事）。

**标签是平铺的多选，`group`（维度）只用于分组显示与排序**，不携带「单选互斥」语义。维度做成互斥（例如「上架状态」只能有一个值）更严谨，但那要引入一套额外的语义、一套校验和一套筛选规则；而多选 + 用户自律已经能回答当前的问题，且互斥是**纯增量**的：将来加一个布尔字段和一条校验即可，不需要动数据模型。

**标签存自己的文档 `product-tags.json`**：`{ tags: [{id, name, group, color, createdAt}], assigns: { "<groupKey>|<tshirtFile>": ["<tagId>", ...] } }`。

- 不放进每条成片记录：一个款式是 **8 条**成片记录，把标签存在记录上就是同一件事的 8 份副本，其中任何一份被单独删掉都会让它们互相矛盾；而且删除单张成片不该让标签跟着抖。
- 不放进 `state.json`：它被客户端轮询并直接渲染，标签赋值会随货架一起长大，塞进去等于每次轮询都拖着整个货架的分类结果。这与 `workflow-runs.json` / `workflow-outputs.json` 当初独立出去是同一条理由，且它有自己的写锁，与另外两份文档互不阻塞。

**接口**（沿用既有 house style：删除/清空走通用的 `/delete`、`/clear` 的 `kind`）：

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/ecom/api/product/tags` | `{ tags, assigns }`，与成品库的 outputs 一起取 |
| POST | `/ecom/api/product/tag` | 新建 / 改名 / 改色 / 换维度（无 `id` 即新建） |
| POST | `/ecom/api/product/tag/apply` | **批量**：`{ keys, add?, remove? }`，一次读改写 |
| POST | `/ecom/api/product/tag/prune` | 清掉指向已不存在款式的赋值记录 |
| POST | `/ecom/api/delete` | `kind: "tag"` |
| POST | `/ecom/api/clear` | `kind: "tags"` |

**未知的 tagId 硬拒（400），未知的款式键则跳过并如实汇报。** 这两者要分开看：前者只可能来自客户端 bug 或过期的标签列表，静默忽略会让界面「看起来点上了其实没有」；后者是**竞态**（选中之后、应用之前，某张成片被删掉了），此时用户对其余卡片的意图依然明确，整批 400 会把一次正常操作变成一次失败——所以施加到还存在的键上，并在响应里报出 `skipped`。这与流水线「一项失败不丢弃整批已付费产物」是同一条既有原则。

**读取时修掉悬空引用，删除时级联，但都不猜测货架。** `assigns` 里指向已删除标签的 id 在读取时被丢弃（一个指向不存在标签的 id 没有任何意义，留着只会让计数虚高）；删除标签时把它从所有赋值里一次摘干净。反过来，**不**在读取时检查「这个款式还在不在」——那要求每次读标签都把 540 KB 的产物库读进来；悬空赋值由客户端的「N 条失效记录 + 一键清理」（`/prune`）处理，**不静默删，也不假装没有**。这与 `workflowGroups` 对已删文件夹的处理一致（留一条无用记录，无害）。

## Alternatives considered

- **把标签打在商品（参考图分组）上**：粒度太粗——「这个颜色先不发、那个颜色发」是真实存在的判断，而一个分组有 1…6 个款式。已否决，改为款式级 + 商品级批量。
- **逻辑键 `cw:<款式id>|<印花文件>`**：能活过强制重跑，但需要反查且老记录解析不出来，引入第三态。已否决，见上。
- **在每条成片记录上加 `tags` 字段**：8 份副本、8 个可能不一致的地方，且删除单张成片会制造歧义。已否决。
- **把标签放进 `state.json`**：它被轮询。已否决，独立文档。
- **维度互斥（单选）**：更严谨但要多一套语义与校验，且是纯增量。本版不做。
- **标签层级 / 布尔筛选表达式（AND-OR-NOT 组合器）**：能表达更复杂的选品逻辑，但要一套查询模型与界面，而当前的问题是「哪些要上架」，多选 AND 已经够。已否决。
- **自动打标签（规则引擎）**：需要一套 DSL 与触发时机定义，且规则一旦写错会静默地标错货。已否决。
- **批量删除成品**：标签是管理，删除是破坏性的；单张删除已在详情页，批量删除留到真有需求时再单独设计（它需要自己的确认语义）。已否决。
- **上架导出（导出成上架用的图片包 + 标题/属性表）**：这是标签的**下游**，标签只负责把集合选出来。不在本次范围内，但接口留好了口子：筛选结果就是导出的输入。

## Consequences

- 新增 `lib/store.js` 的第四份文档 `product-tags.json`（`readTags` / `updateTags`），与 `state.json`、`workflow-runs.json`、`workflow-outputs.json` 并列，各有一条独立写锁。README 的文件布局表与 `store.js` 头部注释同步更新。
- 成品库多了一次并行请求（`/ecom/api/product/tags`），与 outputs 并行发出，不阻塞渲染；标签文档本身很小（当前规模下每个款式一条、几十字节）。
- 货架卡片上多一行彩色胶囊；进入**选择模式**后整卡点击的含义从「打开商品」变成「切换选中」，因此选择模式下弹框不再从卡片打开——这是这次唯一的既有交互改动，且只在选择模式下发生。
- 「全选当前筛选结果」选的是**整个筛选集**，不是当前已渲染的 36 张：货架是 4 列瀑布流 + 分页，按位置做区间选择没有诚实的语义，宁可不做也不做假的。
- 强制重跑后会多出一批**不带标签**的新卡片（旧卡片与旧标签仍在）。v1 在文档里如实说明；v2 按逻辑键继承。
- 删除标签、删除赋值、清空标签都会写 `product-tags.json`；因为该文档有独立写锁，批量应用是**一次**读改写，不会与其它模块的写互相阻塞。
- `card.key`（客户端）与宿主校验用的键必须是同一个形状。两侧是各自独立的半边（客户端不带宿主代码），因此这个形状在两个文件里各写一次，并各自有测试钉住：宿主侧断言「键由 `groupKey|tshirtFile` 组成」，客户端侧断言「卡片的 key 就是 `groupKey|tshirtFile`」。
- 标签的筛选是**客户端**做的：成品库本来就一次取回最多 2000 条产物、在客户端组装成卡片并分页渲染，标签只是给每张卡片再加一次查表。宿主不需要（也不应该）为筛选再开一个查询接口。
