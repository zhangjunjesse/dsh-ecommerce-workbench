# Decision: 印花流水线（第一个真实工作流）

Status: current

## Problem

工作流引擎（DECISION-0002）交付时是空跑的——它证明了自己能调度、能记录、能展示日志，但没有一个真实工作流。用户给出第一个：一组参考截图（同一商品的多个角度）进去，四步之后出来成品：

1. 整组图一起做**印花提取** → 1 张
2. 提示词管理里每个「印花二创-N」跑一次，每次 **2 张** → 4 × 2 = 8 张
3. 每张二创印花 × 每个选中的T恤**款式**（照片），用「印花T恤融合」→ 8 × 3 = 24 张
4. 每件二创T恤跑 **2 轮**、每轮 **4 张**，参考图为「场景图管理里随机一张 + 该二创T恤」→ 24 × 8 = 192 张

**一组 = 1 + 8 + 24 + 192 = 225 次生成调用**，按宿主并发 2、单次 50–90 秒算接近两小时，且每一步都消耗真实额度。这条数字决定了下面几乎所有的设计。

## Decision

新增 `lib/printPipeline.js`（`print.pipeline`，界面名「印花流水线」），在 `BUILT_IN_WORKFLOWS` 中注册。入口：工作流 → 印花流水线（列表里那一行）→ 它自己的详情页。工作流模块因此分为两级——列表只回答"有什么、上次怎么样"，点进去是该工作流自己的页面（设置、它拥有的工作、完整运行记录）。原先把分组面板内联展开在卡片里的做法已废弃（见下方「后续修订」）。

**成品另有独立入口。** 最终产物（第四步的场景成片）在「成品库」里按电商 App 的形式浏览：一个分组 = 一个商品，一个二创T恤 = 一个款式（SKU），该款式的 8 张成片就是它的图集。商品页 = 大图 + 左右切换 + 左侧同款式其它图的缩略图 + 底部款式切换条。这不是另做一套产物，而是同一批成品换一个面向"看货"而不是"操作"的视图。

**收图只有一处：收图目录。** `$DSH_HOME/ecommerce-workbench/workflow-inbox/print.pipeline/`，**一个一级子目录 = 一组**。界面的「上传参考图」把文件写进同一个目录，因此用户说的两条入口（上传 / 放目录）收敛到同一个事实来源，界面只是读目录。

**散在目录根下的图合并成一组「未分组」，而不是每张各成一组。** 单图成组是合法的（一张截图也是一组），所以另一种做法会把同一商品的三张角度图悄悄变成三次 225 次调用的运行，每次只拿到三分之一的信息去提取印花。合并不隐藏代价：估算里会明确警告这一组是散图，怎么处理（拖进子目录）留给用户。

**「款式」= T恤下的一张照片。** 默认选中该 T恤的全部照片（即「所有款式」），用户可以只选某几张。这与既有 T恤二创 的模型一致（它本来也是按照片逐张出图），且与本机数据吻合：1 件T恤 3 张照片 → 3 × 8 = 24。分组上保存了选择；当保存的选择与T恤对不上（照片被删、或换了T恤）时，**回退到默认的「全部」并明说**，而不是退化成「什么都不生成」——回退后的结果正是用户当初没做选择时会得到的结果。

**提示词按名称精确匹配**：`印花提取`、`印花二创-1…N`（按数字后缀排序，不是字典序）、`印花T恤融合`、`换装+裂变`。缺失的不静默跳过：估算逐条列出，跑不到的步骤在计划里报 0。只有「提取」有内置兜底提示词，其余三个是各自步骤的硬前提。

**一次运行只处理一组。** 不把队列一次跑完：一次误操作或一次上游抖动，代价就会从「一组」变成「整个队列」。周期调度正好承担消化队列的职责——设成每小时，已确认的组按顺序一组一组跑。

**调度只消化「已确认」的组。** 周期运行没有人可以事先看估算，所以它只挑显式「确认排队」过的组；没有就什么都不做并说明。**手动运行**是直接点名目标的，所以不需要确认——那一次点击本身就是确认。已完成的组会离开队列；重新「确认排队」会把它放回队列（否则用户补了截图再确认，会静默地什么也不发生）。

**成本先展示、再花，且有硬上限。**「估算并运行」先取 `GET /ecom/api/workflow/estimate`，显示每一步的调用数、会用哪些提示词/T恤/场景池、已经做完多少、以及全部警告，然后由用户确认。运行时用同一份计划对照 `ECOM_WORKFLOW_MAX_CALLS`（默认 **400**，约一组加余量）再查一次，**在第一次调用之前**拒绝。上限还**逐段按实际即将发出的调用数**扣减，而不只看开跑前的估算——否则一个偏乐观的估算就成了唯一能绕开上限的东西。强制重跑按完整计划查，因为它忽略已有产物。

**重跑是续跑，绝不重复付费。** 每个产物都盖上 `workflowId` + `groupKey`（以及它由什么派生而来），所以后一次运行能看出已有什么、只补缺的。这个索引**从产物本身推导**，没有单独的进度台账可以和文件失去同步。跑了一小时中断，再跑就接着走；已经齐全时再跑一次调用数为 0。「强制重跑」是显式要求再来一整轮的入口，它写新行而不是覆盖已经付过钱的那些。

**产物去向：前三步进常规模块，第四步进独立成品库。** 步骤 1–3 写进 印花原图库 / 二创印花 / T恤二创结果（带 `runId` + `groupKey`），因此它们和手工做出来的完全同类，能在工作台其它地方继续用。步骤 4 写进独立成品库（`workflow-outputs.json`）。这个分离不是洁癖：场景图管理是第四步**随机抽图的参考池**，把产出放回去，等于以后拿流水线自己的成品当场景参考，第一次之后每一代都会退化。

**失败语义沿用既有约定。** 每一项独立 try/catch、一成功就落盘，所以一个坏调用不会丢掉整批；有任何失败时这次运行报**失败**（绿色「成功」会掩盖它），摘要说明保留了什么，分组留在队列里等下一次续跑。绝不为了「清理」而删除失败项。

## Alternatives considered

- **一次运行跑完所有待处理组**：省事，但一次误操作或一次上游故障的代价乘以队列长度。已否决，改为「一次一组 + 周期消化」。
- **把第四步产出放回场景图管理**：用户最初的说法是「每个二创T恤都可以得到8个场景图」。已否决并已向用户说明：那会让参考池被自己的产出污染（第四步正是从这个池子随机抽图），画面越跑越崩；改为独立成品库，界面里把它标注为「与场景图管理的参考图池分开」。
- **每张散图各自成组**：会静默把三张角度图变成三次运行。已否决，改为合并 + 明确警告。
- **估算偏乐观时仍按估算放行**：会让上限形同虚设。已否决，改为逐段按实际待办扣减。
- **把「款式」理解为多件T恤**：与本机数据不符（只有 1 件T恤，3 张照片，而用户的例子是 3 款式 → 24），已向用户确认按「照片=款式」实现。
- **给工作流加参数系统（在引擎里）**：只有「跑哪一组」「是否强制」两个参数，且「挑下一个已确认的组」本来就是工作流的领域逻辑。改为引擎只加一个通用的 `ctx.params` 透传，选择逻辑留在工作流内。
- **失败也报成功、只用日志提示**：会掩盖真正没跑完的运行。已否决，有失败即抛错（产物已全部保留）。

## Consequences

- 引擎保持了通用性：`lib/workflowRunner.js` 只多了 `params` 透传与记录；组、估算、成品库这些概念全在 `lib/printPipeline.js`，工作流专属路由也在 `lib/index.js` 里明确标注为「属于某一个工作流」。
- `state.json` 新增 `workflowGroups`（每组的确认/状态/末次结果，以及T恤选择）。组本身在磁盘上，所以删掉一个文件夹只会留下一条无用的记录。
- 新增第三份文档 `workflow-outputs.json`（成品库），与运行历史同理：`/ecom/api/state` 是被轮询并直接渲染的，一组就产出 192 件成品，塞进去会让每次轮询拖着整个库。
- 界面新增流水线专属面板（分组、上传、估算、四阶段成品）。它是唯一展示 225 次这个数字的地方，因此也进了 `test/client-render.test.js` 的组件树渲染测试，连每个阶段渲染出的图片 `src` 都有断言。
- 已确认的一处规模边界：一组的 192 件成品 + 24 行 T恤结果 + 8 张印花会进入常规模块，因此 `/state` 会随已处理组数增长（每组约 +24 行 T恤结果）。**重估条件**：常规模块累积到 `/state` 载荷成为瓶颈时，再给它们上分页或把流水线产物改为只存成品库。当前量级（几十组）不构成瓶颈。
- 成本保护是三层的：估算展示 + 硬上限（逐段扣减）+ 续跑不重复付费。三者都进测试。

## Verification

- `node --check` 全部 8 个 lib 文件 → Passed。
- `node --test "test/*.test.js"` → **89/89 passed**（宿主 67 + 流水线 14 + 客户端 8）。流水线用例逐条断言：一组的 225 次调用（1/8/24/192 分解）、第二次运行零调用、删掉部分末段后只补缺的、强制重跑再付一整轮且不覆盖旧行、上限在任何调用前拒绝且提高后同组放行、缺提示词逐步报告、散图合并与警告、上传重名加后缀与 `../` 越界被拒、确认才能被周期挑走而手动不需要、完成组离开队列且重新确认会回队、成品列出与删除（连字节）、删组保留成品、过期款式选择回退到全部。
- 客户端：`test/client-render.test.js` 用最小 React 桩渲染真实组件树，覆盖工作流**列表**（每个工作流、状态、进入入口）与**详情页**（返回、设置、周期、运行记录、日志）、流水线分组面板（分组列表、估算框含 225 与警告、四个阶段标题，并断言每个阶段实际渲染出了自己的图片）、以及**成品库**（商品网格的封面与计数；商品页的返回、款式数、计数器、左右箭头、左侧缩略图轨、款式切换条、来源与商品信息，并断言每一部分都真的渲染出了自己的图片）。
- **真实数据估算**：把本机真实 `state.json`（10 条提示词、1 件T恤 3 张照片、228 张场景图）复制到临时 store 后估算——四个提示词全部命中、默认选中 3 个款式、1 + 8 + 24 + 192 = 225、**0 条警告**，全程未生成任何东西。
- 浏览器端到端：刷新 profile 拷贝并重启 `dsh web` 后，工作流 → 印花流水线 → 详情页可看到收图目录、上传一组并得到与上表一致的估算；成品库可看到已产出的商品并进入商品页。

## 后续修订（UI 结构）

初版把流水线的分组面板**内联展开**在工作流卡片里，并把四阶段产物摊成一片网格。实际使用后改为：

- **列表 / 详情两级**：卡片只做摘要与入口，所有操作（设置、周期、手动触发、分组队列、运行记录）都进该工作流自己的详情页。
- **成品独立成模块**（「成品库」），按电商 App 的商品页形态呈现（大图 + 左右切换 + 左侧同款式缩略图 + 款式切换条），与"操作台"视图分开：详情页面向操作（队列、成本估算、含中间产物在内的四阶段），成品库面向看货（只看最终成片）。

两处都是**呈现层**的调整：数据、接口、成本护栏、续跑语义都没有变，`state.json` / `workflow-runs.json` / `workflow-outputs.json` 的结构也不变。
